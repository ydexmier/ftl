### SEC-01 — Corriger `ApiResponse.serverError()` : ne pas exposer les messages d'exception au client

**Identifiant :** SEC-01  
**Priorité :** 🟠 Important  
**Effort :** XS  
**Source :** Rapport (audit-dette-2026-08-17.md §1.1)  
**Dépendances :** Aucune

**Contexte :**  
`ApiResponse.serverError(err)` retourne le message de l'exception Node.js directement dans le corps HTTP 500. En cas d'erreur Mongoose (doublon de clé, timeout, document invalide), le message contient le nom de collection, les clés, et parfois les valeurs. Ce message est visible par n'importe quel client HTTP qui observe un 500.

**Critères d'acceptation :**
- [ ] `ApiResponse.serverError()` retourne `{ error: 'Internal server error' }` en JSON (message générique)
- [ ] Le détail de l'exception est toujours loggé côté serveur (via `console.error` ou logger structuré)
- [ ] Les 24 routes qui appellent `ApiResponse.serverError(err)` bénéficient du fix sans modification de leur code
- [ ] Un test confirme que le status 500 est retourné avec le message générique (pas le message d'exception)

### SEC-02 — Migrer le rate limiter vers un backend partagé (Redis/Upstash)

**Identifiant :** SEC-02  
**Priorité :** 🟠 Important (conditionnel au contexte de déploiement)  
**Effort :** M  
**Source :** Rapport (audit-dette-2026-08-17.md §1.2)  
**Dépendances :** Aucune

**Contexte :**  
Le rate limiter actuel (`src/lib/auth/rateLimit.ts`) utilise un `Map` Node.js in-process. Il est réinitialisé à chaque cold start et n'est pas partagé entre instances. En déploiement multi-instances ou multi-region, un attaquant peut distribuer ses requêtes et contourner la limite. Les 6 endpoints critiques protégés (`/login`, `/forgot-password`, `/reset-password`, `/access-requests`, `/invitations`, `/guest/validate`) ne sont alors que symboliquement protégés.

**Critères d'acceptation :**
- [ ] Le rate limiter utilise un backend externe partagé (Redis via `ioredis` ou Upstash via `@upstash/ratelimit`)
- [ ] L'interface `checkRateLimit(key)` reste identique — aucune modification dans les routes appelantes
- [ ] En cas d'indisponibilité du backend Redis, le rate limiter fail-open (laisse passer) avec un log d'alerte
- [ ] Les 6 endpoints existants continuent de fonctionner avec les mêmes paramètres (5 tentatives / 15 min)
- [ ] Les tests existants sur le rate limiting sont adaptés (mock du backend Redis)
- [ ] Une variable d'environnement `REDIS_URL` est documentée dans `.env.example`

### TEST-01 — Ajouter les tests d'intégration pour l'approbation admin des invités

**Identifiant :** TEST-01  
**Priorité :** 🟠 Important  
**Effort :** S  
**Source :** Rapport (audit-dette-2026-08-17.md §3.1, coverage-2026-08-17.md Lot 1)  
**Dépendances :** Aucune

**Contexte :**  
Les routes `GET /api/groups/[id]/tournaments/[tid]/guests` et `PUT /api/groups/[id]/guests/[accessId]` gèrent l'approbation, le rejet et la révocation des accès invités. La route PUT a 3 branches logiques distinctes et envoie un email lors d'une approbation. Ces routes ne sont couvertes par aucun fichier de test.

**Critères d'acceptation :**
- [ ] Fichier `src/__tests__/guest-approval.test.ts` créé
- [ ] `GET /api/groups/[id]/tournaments/[tid]/guests` :
  - [ ] Retourne 401 sans session
  - [ ] Retourne 403 si pas admin du groupe
  - [ ] Retourne liste vide si aucun accès PENDING
  - [ ] Retourne les invités avec `username` et `email` enrichis
- [ ] `PUT /api/groups/[id]/guests/[accessId]` :
  - [ ] Retourne 401 sans session
  - [ ] Retourne 403 si pas admin du groupe
  - [ ] Retourne 400 si `action` invalide
  - [ ] Retourne 403 si l'`accessId` n'appartient pas au groupe `id`
  - [ ] `approve` : status PENDING → ACCEPTED, retourne 400 si status ≠ PENDING
  - [ ] `reject` : status PENDING → REJECTED, retourne 400 si status ≠ PENDING
  - [ ] `revoke` : status → REVOKED, retourne 400 si déjà REVOKED/EXPIRED/REJECTED
