## SEC-01 — Rate limiting sur l'endpoint Bearer token public

**Identifiant :** SEC-01  
**Priorité :** 🟠 Important  
**Effort :** XS  
**Source :** Rapport  

**Contexte :** L'endpoint `GET /api/external/tournaments/[id]/players` est public (pas de session cookie) et authentifie via Bearer token. Aucun rate limiting n'est appliqué sur les authentifications échouées, permettant un brute-force de tokens valides et une charge non bornée sur le serveur.

**Critères d'acceptation :**
- [ ] `checkRateLimit('external-api:IP')` est appelé en tête du handler
- [ ] Une réponse `429` avec `retryAfter` est retournée si la limite est dépassée
- [ ] La clé de rate limit est namespaced distinctement des autres endpoints
- [ ] Un test vérifie le comportement 429 après dépassement
- [ ] La logique `getIp` est importée depuis `src/lib/auth/getIp.ts` (pas réimplémentée inline)

**Dépendances :** Aucune

## SEC-02 — Tests d'intégration pour les routes invités (autorisation)

**Identifiant :** SEC-02  
**Priorité :** 🟠 Important  
**Effort :** M  
**Source :** Rapport  

**Contexte :** Quatre routes liées aux accès invités (magic-link, guests, my-tournaments, révocation) n'ont aucun test d'intégration. Elles contiennent de la logique d'autorisation critique : un invité dont l'accès est révoqué doit être rejeté même si sa session est encore valide. Cette invariante n'est pas vérifiée automatiquement.

**Critères d'acceptation :**
- [ ] `GET /api/guest/my-tournaments` : retourne le tournoi de l'accès accepté
- [ ] `GET /api/guest/my-tournaments` : retourne 403 si accès révoqué (status REVOKED)
- [ ] `GET /api/guest/my-tournaments` : retourne 403 si accès expiré
- [ ] `GET /api/guest/my-tournaments` : retourne 401 si non authentifié
- [ ] `GET /api/groups/[id]/tournaments/[tid]/guests` : liste les accès (admin only)
- [ ] `GET /api/groups/[id]/tournaments/[tid]/guests` : retourne 403 si non admin
- [ ] `DELETE /api/groups/[id]/guests/[accessId]` : révoque l'accès (status → REVOKED)
- [ ] `DELETE /api/groups/[id]/guests/[accessId]` : retourne 403 si non admin du groupe
- [ ] `DELETE /api/groups/[id]/guests/[accessId]` : retourne 404 si accessId inexistant
- [ ] Tous les tests utilisent MongoDB Memory Server et le pattern habituel du projet

**Dépendances :** Aucune

## SEC-03 — Tests d'intégration pour les routes magic-link

**Identifiant :** SEC-03  
**Priorité :** 🟠 Important  
**Effort :** S  
**Source :** Rapport  

**Contexte :** La route `POST /api/groups/[id]/tournaments/[tid]/magic-link` génère des tokens de sécurité UUID et doit garantir qu'un seul lien est actif par groupe+tournoi (l'ancien est désactivé à chaque rotation). Cette invariante de sécurité (un seul token actif) n'est pas vérifiée par des tests automatiques.

**Critères d'acceptation :**
- [ ] `POST` génère un token UUID unique
- [ ] `POST` désactive l'ancien token avant d'en créer un nouveau
- [ ] `GET` retourne le lien actif s'il existe
- [ ] `GET` retourne 404 si aucun lien actif
- [ ] Les deux méthodes retournent 403 si l'appelant n'est pas admin du groupe
- [ ] Après rotation, l'ancien token n'est plus accepté par `/api/guest/validate`

**Dépendances :** Aucune

## ARCH-02 — Remplacer les fetch directs par `useFetch` dans les composants

**Identifiant :** ARCH-02  
**Priorité :** 🟠 Important  
**Effort :** L  
**Source :** Rapport  

**Contexte :** 17 composants React effectuent des appels `fetch()` manuels dans des `useEffect` alors que le hook `useFetch<T>(url)` existe et expose exactement `{ data, loading, error, refetch }`. `Tournament.tsx` est le cas le plus criant : il importe déjà `useFetch` pour un endpoint (ligne 81) puis l'ignore pour 7 autres GET dans le même fichier. Cette incohérence produit des patterns de gestion d'erreur et de loading différents dans chaque composant.

**Critères d'acceptation :**
- [ ] `Tournament.tsx` utilise `useFetch` pour ses 7 GET (conflicts, last-round, me, my-role, merge-status, uncertainties, admin-groups)
- [ ] `GroupTournaments.tsx` utilise `useFetch` pour ses 3 GET
- [ ] `GroupTournamentScoutingPage.tsx` utilise `useFetch` pour ses 2 GET
- [ ] `PlayersTab.tsx` utilise `useFetch` pour ses 2 GET
- [ ] Les autres composants (GuestInviteModal, PlayerCommentHistory, ReportsTab, etc.) utilisent `useFetch` pour leurs GET de chargement initial
- [ ] Les GET qui nécessitent un re-fetch conditionnel (ex. après mutation) utilisent le `refetch` de `useFetch` plutôt qu'un `useState` + `useEffect` manuel
- [ ] Aucune régression fonctionnelle sur les composants migrés

**Dépendances :** Aucune (refactoring pur)

## TS-01 — Typer les pipelines MongoDB avec `PipelineStage[]`

**Identifiant :** TS-01  
**Priorité :** 🟡 Mineur  
**Effort :** S  
**Source :** Rapport  

**Contexte :** 7 occurrences de `any` ou `any[]` dans deux repositories (`RoundRepository.ts`, `TournamentPlayersDeckRepository.ts`), toutes utilisées pour typer des pipelines d'agrégation MongoDB. Le type `PipelineStage` de mongoose v7 permet de supprimer ces `any` avec une validation TypeScript complète.

**Critères d'acceptation :**
- [ ] `import type { PipelineStage } from 'mongoose'` ajouté dans les deux fichiers
- [ ] Les 7 occurrences de `any` / `any[]` remplacées par `PipelineStage[]` ou le type Mongoose approprié
- [ ] TypeScript compile sans erreur après la modification (`tsc --noEmit`)
- [ ] Les tests existants passent sans modification (`npm test`)
- [ ] Aucun `as any` résiduel dans les deux fichiers

**Dépendances :** Aucune

**Priorité :** 🟡 Mineur  
**Effort :** S  
**Source :** Rapport
