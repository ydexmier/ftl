## PERF-01 — N+1 query dans les routes sidebar tournoi

**Catégorie :** Performance  
**Source :** Rapport  
**Priorité :** 🟠 Important  
**Effort :** S  
**Dépendances :** aucune

### Contexte

Les routes `GET /api/tournaments/[id]/admin-groups` et `GET /api/tournaments/[id]/member-groups` font N requêtes `GroupRepository.findById()` dans un `Promise.all` — une par groupe lié au tournoi. Pour un tournoi appartenant à 10 groupes, cela génère 11 requêtes MongoDB au lieu de 2.

Ces routes sont appelées au chargement de la page tournoi (dans `Tournament.tsx`), ce qui pénalise le temps de réponse initial de l'interface.

### Critères d'acceptation

- [ ] `GroupRepository` expose une méthode `findByIds(ids: string[]): Promise<IGroup[]>` (analogue à `UserRepository.findByIds`)
- [ ] `app/api/tournaments/[id]/admin-groups/route.ts` : remplace la boucle de `findById` par un `findByIds` batch suivi d'un filtre en mémoire
- [ ] `app/api/tournaments/[id]/member-groups/route.ts` : même correction
- [ ] Les deux routes conservent leur comportement observable (même réponse JSON)
- [ ] `npm test` passe à 100% après les changements

## SEC-01 — Tests pour approve/reject/revoke des accès invités

**Catégorie :** Tests · Sécurité  
**Source :** Rapport  
**Priorité :** 🔴 Critique  
**Effort :** M  
**Dépendances :** aucune

### Contexte

`PUT /api/groups/[id]/guests/[accessId]` (60 lignes) est la route qui approuve, rejette ou révoque un accès invité à un groupe. Elle contient la logique de transition d'état la plus complexe parmi les routes non testées, avec un envoi d'email conditionnel (`sendGuestApprovedEmail`). En l'absence de tests, une régression pourrait permettre des approbations non autorisées ou des états incohérents (ex. approuver un accès déjà REVOKED).

### Critères d'acceptation

- [ ] Fichier `src/__tests__/guest-access-actions.test.ts` créé (ou ajout dans `guest-access.test.ts`)
- [ ] `PUT` sans auth → 401
- [ ] `PUT` avec action invalide (`"ban"`, `"suspend"`, etc.) → 400
- [ ] `PUT` par un non-admin du groupe → 403
- [ ] `PUT` avec accessId inconnu → 404
- [ ] `PUT approve` sur accès non-PENDING → 400
- [ ] `PUT approve` valide → status ACCEPTED dans la DB
- [ ] `PUT approve` valide → `sendGuestApprovedEmail` appelé (mocké)
- [ ] `PUT reject` sur accès non-PENDING → 400
- [ ] `PUT reject` valide → status REJECTED dans la DB
- [ ] `PUT revoke` sur accès REVOKED/EXPIRED/REJECTED → 400
- [ ] `PUT revoke` valide (status ACCEPTED) → status REVOKED dans la DB
- [ ] `npm test` passe à 100%

## TEST-02 — Tests pour les routes magic-link et guests

**Source :** Rapport

- `GET /api/groups/[id]/tournaments/[tid]/guests` — liste des accès en attente pour le groupe

- [ ] `POST` valide → crée un nouveau token UUID actif

**guests (liste) :**
- [ ] `GET` sans auth → 401
- [ ] `GET` non-admin → 403
- [ ] `GET` valide → liste des accès avec username/email hydraté depuis User
- [ ] Les accès ACCEPTED n'apparaissent pas dans la liste

**my-tournaments :**
- [ ] `GET` sans auth → 401
- [ ] Aucun accès → `{ tournaments: [] }`
- [ ] Un accès ACCEPTED → `{ tournaments: [{ accessId, groupId, tournamentId, tournamentName, status, expiresAt }] }`
