## ARCH-01 — Extraire la logique métier de `history/route.ts` vers `PlayerHistoryService`

**Contexte :** Les fonctions `buildResult()` et `buildScores()` ainsi que la boucle de construction de l'historique sont définies directement dans `app/api/tournaments/[id]/players/[playerId]/history/route.ts`. Cela viole le principe "pas de logique métier dans les routes" défini dans CLAUDE.md. Ces fonctions sont testables unitairement et réutilisables.

**Critères d'acceptation :**
- [ ] `buildResult()` et `buildScores()` sont déplacées dans `src/services/PlayerHistoryService.ts`
- [ ] La boucle de construction de `history[]` est dans `PlayerHistoryService.getHistory(tournamentId, playerId, scope)`
- [ ] Le handler `history/route.ts` se réduit à : auth + scope check + appel `PlayerHistoryService.getHistory()` + retour JSON
- [ ] Les tests existants dans `player-history.test.ts` passent sans modification
- [ ] Des tests unitaires pour `buildResult` couvrent les 5 cas : BYE, DRAW, WIN, LOSS, PENDING

**Effort :** S  
**Dépendances :** Aucune  
**Source :** Rapport (ARCH)

## PERF-01 — Remplacer le N+1 dans `GET /api/admin/groups` par une aggregation

**Contexte :** Le handler `app/api/admin/groups/route.ts` effectue 2N+1 requêtes DB pour lister N groupes : une `findAll()` puis, pour chaque groupe, un `findById()` (pour compter les membres) et un `findByGroupId()` (pour compter les tournois). Avec un parc de groupes croissant, cette page admin sera de plus en plus lente.

**Critères d'acceptation :**
- [ ] `GroupRepository` expose une méthode `findAllEnriched()` utilisant une aggregation MongoDB avec `$lookup` sur `grouptournaments`
- [ ] L'aggregation retourne directement `memberCount` et `tournamentCount` via `$size`
- [ ] Le handler `GET /api/admin/groups` n'effectue plus qu'un seul aller-retour DB pour la liste enrichie
- [ ] La méthode `findAllEnriched()` est couverte par un test dans `admin-groups.test.ts`
- [ ] La réponse API reste identique (même shape) — pas de breaking change côté client

**Effort :** S  
**Dépendances :** Aucune  
**Source :** Rapport (PERF)

## TEST-01 — Tests unitaires pour `buildResult` / `buildScores` (isolation)

**Contexte :** `buildResult` gère 5 cas distincts (BYE, DRAW, WIN, LOSS, PENDING) et est actuellement testé uniquement via le handler de route. Une fois extrait dans `PlayerHistoryService` (ARCH-01), ces fonctions peuvent être testées unitairement avec des fixtures légères, sans passer par MongoDB.

**Critères d'acceptation :**
- [ ] `buildResult` : test pour chaque cas — BYE (`match_is_bye=true`), LOSS (`match_is_loss=true`), DRAW (intentional + unintentional + `games_drawn`), PENDING (`winning_player=null`), WIN et LOSS ordinaires
- [ ] `buildScores` : test pour winner, loser, et match non terminé (`winning_player=null`)
- [ ] Les tests sont dans `player-history-rules.test.ts` (nouveau fichier, tests purs sans DB)

**Effort :** S  
**Dépendances :** ARCH-01  
**Source :** Rapport (TEST + ARCH)

## TEST-02 — Tests pour la révocation d'accès invité

**Contexte :** `DELETE /api/groups/external-access/[accessId]` (révocation d'un accès invité) et `POST /api/groups/[id]/tournaments/[tid]/external-access` (création d'un accès via magic link) n'ont pas de tests d'intégration. Ces routes touchent la sécurité d'accès (l'invité ne doit plus pouvoir accéder après révocation).

**Critères d'acceptation :**
- [ ] `DELETE` — 401 sans session ; 403 si pas admin du groupe ; 200 + status REVOKED si admin
- [ ] Après révocation, `GET /api/guest/my-tournaments` ne retourne plus le tournoi révoqué pour cet invité
- [ ] `POST external-access` — 401 sans auth ; 403 si pas admin ; 200 avec token généré ; un seul lien actif à la fois (le précédent est désactivé)
- [ ] Email mocké (pas de vrai envoi en test)

**Effort :** M  
**Dépendances :** Aucune  
**Source :** Rapport (TEST)

## TS-01 — Typer les pipelines MongoDB avec `PipelineStage[]`

**Contexte :** 7 usages de `any` subsistent dans les pipelines d'agrégation MongoDB (`RoundRepository.ts` et `TournamentPlayersDeckRepository.ts`). `PipelineStage` de Mongoose v7 permet de supprimer ces `any` tout en gardant la validation TypeScript.

**Critères d'acceptation :**
- [ ] `import type { PipelineStage } from 'mongoose'` ajouté dans les deux fichiers
- [ ] Les 4 usages de `any[]` dans `RoundRepository.ts` remplacés par `PipelineStage[]`
- [ ] Les 3 usages dans `TournamentPlayersDeckRepository.ts` remplacés
- [ ] `npm test` passe sans erreur TypeScript (`tsc --noEmit`)

**Effort :** S  
**Dépendances :** Aucune  
**Source :** Rapport (TS)

## TEST-04 — Tests pour les hooks React non couverts

**Contexte :** `useFetch`, `useTournamentManagement`, `usePlayerHistory`, `useTournamentStats`, et `useScrollGuard` n'ont pas de tests. Ces hooks sont utilisés dans de nombreux composants et leur comportement (loading, error, re-fetch) n'est validé qu'implicitement via les E2E.

**Critères d'acceptation :**
- [ ] `useFetch` : loading=true pendant la requête ; data rempli au succès ; error rempli en cas d'échec ; re-fetch déclenché après `refresh()`
- [ ] `useTournamentManagement` : archive/désarchive change le status ; refresh met à jour la liste
- [ ] `usePlayerHistory` : charge l'historique pour un playerId ; gère le cas groupId
- [ ] Tests dans `src/__tests__/hooks/` avec fetch mocké (MSW ou vi.mock)
