## 🔴 Sprint immédiat

### [SEC-001] Ajouter l'authentification DB sur `POST /api/rounds/[roundId]/matchs`

**Type :** `fix(security)`  
**Effort estimé :** XS (< 30 min)  
**Fichier :** `app/api/rounds/[roundId]/matchs/route.ts`

**Contexte :**  
Le handler POST de cette route ne vérifie pas la session MongoDB — seule la signature HMAC du cookie est contrôlée par le middleware Edge. Un utilisateur avec un cookie HMAC valide (même pour une session expirée ou révoquée en base) peut écraser n'importe quel document Round avec des données arbitraires.

**Travail :**
- Ajouter `const auth = await getAuthSession(request);` en début de handler
- Retourner `ApiResponse.unauthorized()` si `auth` est null
- Vérifier si la route doit être réservée aux admins (si oui : utiliser `requireAdminSession`)
- Ajouter un test d'intégration : appel sans session → 401

**Définition de fini :**  
`npm test` vert, test d'intégration couvrant le cas non-authentifié.

### [SEC-002] Masquer les `sessionId` bruts dans `GET /api/admin/users/[id]/sessions`

**Type :** `fix(security)`  
**Effort estimé :** XS (< 30 min)  
**Fichiers :** `src/repositories/db/SessionRepository.ts`, `app/api/admin/users/[id]/sessions/route.ts`

**Contexte :**  
`SessionRepository.findByUserId()` retourne les documents complets y compris le champ `sessionId`, qui est le token d'authentification. La route admin expose ces tokens à tout administrateur qui consulte les sessions d'un utilisateur — permettant l'usurpation d'identité sans mot de passe.

**Travail :**

- Vérifier que le type de retour (interface TypeScript) reflète l'exclusion
- Ajouter un test d'intégration : vérifier que `sessionId` est absent de la réponse

**Définition de fini :**  
`npm test` vert, test d'intégration vérifiant l'absence de `sessionId` dans la réponse JSON.

## 🟠 Sprint courant

### [SEC-003] Protéger les recherches MongoDB contre les injections ReDoS

**Type :** `fix(security)`  
**Effort estimé :** S (2–3h)  
**Fichiers :** `src/lib/validation.ts`, `src/repositories/db/UserRepository.ts`, `TournamentRepository.ts`, `TournamentPlayersDeckRepository.ts`, `AuditLogRepository.ts`, `RoundRepository.ts`

**Contexte :**  
5 repositories passent les paramètres de recherche directement dans `{ $regex: userInput, $options: 'i' }` sans échapper les caractères spéciaux. Une expression comme `(a+)+$` peut provoquer une Catastrophic Backtracking côté MongoDB et saturer le CPU.

**Travail :**
- Ajouter dans `src/lib/validation.ts` :
  ```typescript
  export function escapeRegex(s: string): string {
    return s.replace(/[.*+?^${}()|[\]\\]/g, '\\$&');
  }
  ```
- Remplacer `{ $regex: search }` par `{ $regex: escapeRegex(search) }` dans les 5 repositories (environ 8 occurrences)
- Ajouter un test unitaire dans `validation.test.ts` pour `escapeRegex`

**Définition de fini :**  
`npm test` vert, `escapeRegex` testée, tous les `$regex` avec entrée utilisateur sont protégés.

### [ARCH-001] Éliminer la requête N+1 dans `GET /api/admin/groups`

**Type :** `fix(perf)`  
**Effort estimé :** S (2–3h)  
**Fichier :** `app/api/admin/groups/route.ts`, `src/repositories/db/GroupRepository.ts`, `src/repositories/db/GroupTournamentRepository.ts`

**Contexte :**  
La route liste tous les groupes puis fait N appels `findById()` + N appels `findByGroupId()` — soit 2N+1 requêtes MongoDB pour N groupes. Pour 50 groupes : 101 requêtes.

**Travail :**
- Ajouter `GroupRepository.findAllWithCounts()` : aggregation `$project { name, memberCount: { $size: '$members' }, isPinned }`
- Ajouter `GroupTournamentRepository.countByGroupIds(ids: string[])` : aggregation `$group { _id: '$groupId', count: { $sum: 1 } }`
- Refactorer le handler pour utiliser ces deux méthodes (2 requêtes au lieu de 2N+1)
- Ajouter un test d'intégration couvrant la route avec plusieurs groupes

**Définition de fini :**  
`npm test` vert, test de la route avec ≥ 3 groupes.

### [DETTE-001] Valider la longueur du username dans `PATCH /api/user/profile`

**Type :** `fix(validation)`  
**Effort estimé :** XS (< 30 min)  
**Fichier :** `app/api/user/profile/route.ts`

**Contexte :**  
La contrainte `maxlength: 30` du modèle Mongoose est silencieuse côté API — pas de message d'erreur métier. L'UI peut envoyer un username trop long sans recevoir de 400 explicite.

**Travail :**
- Ajouter avant l'appel `UserRepository.update()` :
  ```typescript
  const trimmed = username.trim();
  if (!trimmed || trimmed.length > 30) {
    return ApiResponse.badRequest('Le nom doit faire entre 1 et 30 caractères');
  }
  ```
- Compléter le test `user-profile.test.ts` : cas username vide → 400, username > 30 chars → 400

**Définition de fini :**  
`npm test` vert, 2 cas de test ajoutés.
