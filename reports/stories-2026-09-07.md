### SEC-01 — Rate limiting manquant sur l'API externe Bearer token

**Identifiant :** SEC-01  
**Priorité :** 🔴 Critique  
**Effort :** XS  
**Source :** Rapport

**Contexte :** La route `GET /api/external/tournaments/[id]/players` est authentifiée uniquement par un Bearer token. Aucun rate limiting n'est en place, ce qui permet à un attaquant de tester des tokens en rafale (brute-force) sans défense applicative. Chaque tentative déclenche un `hashToken(raw)` + lookup MongoDB, représentant un coût CPU et un vecteur d'attaque réel.

**Critères d'acceptation :**
- [ ] `checkRateLimit('ext-api:<IP>')` est appelé en tête du handler GET
- [ ] Si la limite est dépassée, retourne `ApiResponse.tooManyRequests(...)` (429)
- [ ] `getIp(request)` de `src/lib/auth/getIp.ts` est utilisé (pas de duplication)
- [ ] Un test d'intégration vérifie qu'après N tentatives, la Nième retourne 429

**Dépendances :** Aucune

### REFACTO-01 — Homogénéiser `NextResponse.json()` → `ApiResponse` dans 3 routes

**Identifiant :** REFACTO-01  
**Priorité :** 🟠 Important  
**Effort :** S  
**Source :** Rapport

**Contexte :** Trois routes utilisent `NextResponse.json()` directement au lieu d'`ApiResponse` (convention du projet) : `app/api/auth/login/route.ts` (4 occurrences), `app/api/auth/refresh/route.ts` (1), `app/api/guest/validate/route.ts` (1). Cette incohérence n'a pas d'impact fonctionnel mais complique la maintenance et masque l'intention.

**Critères d'acceptation :**
- [ ] `app/api/auth/login/route.ts` : tous les `NextResponse.json(...)` remplacés par `ApiResponse.*`
- [ ] `app/api/auth/refresh/route.ts` : `NextResponse.json({}, { status: 200 })` remplacé par `ApiResponse.ok({})`
- [ ] `app/api/guest/validate/route.ts` : `NextResponse.json({ tournamentId, groupId })` remplacé par `ApiResponse.ok({ tournamentId, groupId })`
- [ ] `.cookies.set()` fonctionne toujours correctement après la migration (login + validate + refresh)
- [ ] Les tests existants (`auth-login.test.ts`, `auth-refresh.test.ts`, `guest-access.test.ts`) passent sans modification

**Dépendances :** Aucune

### TEST-01 — Tests d'intégration pour la route `magic-link`

**Identifiant :** TEST-01  
**Priorité :** 🟠 Important  
**Effort :** M  
**Source :** Rapport

**Contexte :** `app/api/groups/[id]/tournaments/[tid]/magic-link/route.ts` gère la génération et la révocation de tokens UUID pour les accès invités. C'est un flux critique (point d'entrée du parcours invité) entièrement non couvert. Le repository `GroupMagicLinkRepository` (upsert, deactivate) n'est pas testé non plus.

**Critères d'acceptation :**
- [ ] POST sans auth → 401
- [ ] POST par non-admin du groupe → 403
- [ ] POST par admin → retourne `{ token: string }` de format UUID valide
- [ ] POST une 2e fois → l'ancien lien est désactivé (`isActive: false`) et un nouveau est créé
- [ ] GET par admin → retourne le lien actif avec son token
- [ ] GET si aucun lien actif → retourne null ou 404
- [ ] DELETE par admin → désactive le lien ; GET retourne null
- [ ] Connexion avec un token révoqué (via `POST /api/guest/validate`) → 401 ou token invalide
- [ ] Fichier de test : `src/__tests__/magic-link.test.ts` ou ajout dans `guest-access.test.ts`

**Dépendances :** Aucune (GroupMagicLinkRepository est déjà implémenté)

### TEST-03 — Tests d'intégration pour `users/search` et `guest/my-tournaments`

**Priorité :** 🟠 Important  
**Effort :** S

- [ ] Invité avec accès REVOKED → tournoi absent

### TS-01 — Définir les types `*Populated` pour les documents Mongoose peuplés

**Identifiant :** TS-01  
**Priorité :** 🟡 Mineur  
**Effort :** S  
**Source :** Rapport

**Contexte :** Trois points d'usage dans les Server Components castent des résultats Mongoose peuplés avec `as unknown as {...}`, faute de types dédiés. Ces casts masquent les erreurs de typage et compliquent les évolutions futures.

**Critères d'acceptation :**
- [ ] `src/types/invitation.ts` contient un type `InvitationPopulated` avec `invitedBy: { username: string } | null` et `groupIds: { _id: string; name: string }[]`
- [ ] `app/admin/invitations/page.tsx` (lignes 41–42) utilise `InvitationPopulated` au lieu du cast `as unknown as`
- [ ] `app/register/[token]/page.tsx` (ligne 41) utilise `InvitationPopulated` au lieu du cast
- [ ] `app/api/tournaments/[id]/players/[playerId]/comments/route.ts` (ligne 47) : type union `ObjectId | { _id: ObjectId }` ou type `CommentPopulated` défini dans `src/types/`
- [ ] Aucun `as unknown as` résiduel pour ces cas
- [ ] TypeScript compile sans erreur (`tsc --noEmit`)

**Dépendances :** Aucune
