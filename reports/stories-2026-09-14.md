### ARCH-01 — Refactoriser les pages admin pour passer par les repositories

**Contexte :**  
Trois pages Server Components dans `app/admin/` importent et interrogent directement des modèles Mongoose (`UserModel`, `SessionModel`, `AuditLogModel`, `InvitationModel`), en violation explicite de l'architecture définie dans CLAUDE.md : "Accès MongoDB exclusivement via les repositories — jamais de requêtes Mongoose directes dans les routes ou services."

Cette violation crée du couplage direct entre les pages et la couche Mongoose, contourne les conventions de pagination/tri des repositories, et rend ces pages non-testables unitairement.

**Fichiers concernés :**
- `app/admin/users/page.tsx` (lignes 34, 40)
- `app/admin/users/[id]/page.tsx` (lignes 14, 21, 25, 26)
- `app/admin/invitations/page.tsx` (lignes 24, 31)

**Critères d'acceptation :**
- [ ] `app/admin/users/page.tsx` ne contient plus d'import de `UserModel` — la requête paginée passe par `UserRepository.findWithFilters()` (méthode à créer si absente)
- [ ] `app/admin/users/[id]/page.tsx` ne contient plus d'imports de `UserModel`, `SessionModel`, `AuditLogModel` — les accès passent par les repositories correspondants (ajouter méthodes si nécessaires)
- [ ] `app/admin/invitations/page.tsx` ne contient plus d'import de `InvitationModel` — passe par `InvitationRepository`
- [ ] Les méthodes ajoutées aux repositories sont couvertes par les tests existants ou de nouveaux cas
- [ ] `npm test` passe à 100%

**Effort estimé :** M  
**Dépendances :** aucune  
**Priorité :** 🔴 Critique  
**Source :** Rapport

### ARCH-03 — Déplacer le filtrage de conflits côté serveur dans `Tournament.tsx`

**Contexte :**  
`components/tournament/Tournament.tsx` (lignes 133, 141) récupère tous les conflits et incertitudes d'un groupe, puis filtre côté client par `tournamentId`. Les endpoints `GET /api/groups/[id]/conflicts` et `/uncertainties` ne supportent pas de paramètre `?tournamentId=`. Pour un groupe actif sur plusieurs tournois, cela transfère des données inutiles au client.

**Critères d'acceptation :**
- [ ] Les routes `GET /api/groups/[id]/conflicts` et `GET /api/groups/[id]/uncertainties` acceptent un paramètre optionnel `?tournamentId=`
- [ ] Quand `tournamentId` est fourni, le filtre est appliqué côté serveur dans le repository/service
- [ ] `Tournament.tsx` utilise `?tournamentId=${id}` dans les appels fetch
- [ ] Les filtres `.filter(c => c.tournamentId === Number(id))` côté client sont supprimés
- [ ] Tests d'intégration couvrent le cas filtré et le cas non filtré

**Effort estimé :** S  
**Dépendances :** aucune  
**Priorité :** 🟡 Mineur  
**Source :** Rapport

### REFACTO-01 — Migrer les 14 fetch GET inline vers le hook `useFetch`

**Contexte :**  
14 composants React contiennent des `fetch()` GET dans des `useEffect` ou callbacks au lieu d'utiliser le hook `useFetch<T>(url)` fourni dans `src/hooks/useFetch.ts`. Le hook gère déjà le loading, l'error et le re-fetch. Cette dette crée une incohérence dans la gestion des états de chargement et multiplie les patterns de fetch différents dans le projet.

**Fichiers concernés :**
- `components/tournament/Tournament.tsx` (8 fetch — Lot 1 prioritaire)
- `components/ui/PlayerCommentHistory.tsx`
- `components/tournament/ConflictResolutionModal.tsx`
- `components/tournament/PlayersTab.tsx` (2 fetch)
- `components/tournament/GuestInviteModal.tsx` (2 fetch)
- `components/tournament/ReportsTab.tsx`
- `components/admin/users/AdminMemoModal.tsx`
- `components/admin/groups/InviteMemberModal.tsx`
- `components/admin/invitations/InvitationSendModal.tsx`
- `components/admin/users/AddToGroupModal.tsx`
- `components/admin/AdminSidebar.tsx`
- `components/ui/Layout.tsx`
- `components/round/Round.tsx`

**Critères d'acceptation :**
- [ ] Tous les GET fetch dans `useEffect` des 13 fichiers ci-dessus sont remplacés par `useFetch<T>(url)`
- [ ] Les états `loading` et `error` sont gérés via les valeurs retournées par `useFetch` (pas de state local dupliqué)
- [ ] L'appel `/api/auth/me` dans `Tournament.tsx` (ligne 107) est supprimé — l'identité utilisateur est récupérée depuis le store Zustand existant
- [ ] Aucun comportement utilisateur ne change (les données sont fetched au même moment)
- [ ] `npm test` passe à 100%

**Effort estimé :** L  
**Dépendances :** aucune  
**Priorité :** 🟠 Important  
**Source :** Rapport

### TEST-01 — Tests d'intégration pour la route magic-link

**Contexte :**  
`app/api/groups/[id]/tournaments/[tid]/magic-link/route.ts` est le point d'entrée du flux d'accès invité (génération du token, envoi email). Elle n'a aucun test d'intégration alors que `POST /api/guest/validate` (étape suivante du flux) est couvert. L'absence de tests sur la génération expose des régressions silencieuses sur cette route critique.

**Critères d'acceptation :**
- [ ] Nouveau fichier `src/__tests__/magic-link.test.ts` (ou intégration dans `groups-tournaments.test.ts`)
- [ ] `POST /magic-link` par admin du groupe → retourne 200 avec le token, ancien token désactivé en DB
- [ ] `POST /magic-link` par non-admin → 403
- [ ] `POST /magic-link` sans auth → 401
- [ ] `POST /magic-link` avec groupId ou tournamentId inconnu → 404
- [ ] `GET /magic-link` par admin → retourne le token actif (ou `null` si inexistant)
- [ ] `GET /magic-link` sans auth → 401
- [ ] `npm test` passe à 100%

**Effort estimé :** S  
**Dépendances :** aucune  
**Priorité :** 🔴 Critique  
**Source :** Rapport

### TEST-02 — Tests d'intégration pour les routes guests et `my-tournaments`

**Contexte :**  
Trois routes liées aux invités n'ont aucun test : le listing des invités d'un groupe (`/guests/`), le détail d'un accès invité (`/guests/[accessId]`), et les tournois accessibles à un compte isGuest (`/guest/my-tournaments`). Ces routes sont fonctionnellement liées au flux déjà couvert par `guest-access.test.ts` mais leurs propres comportements (filtrage par statut REVOKED, contrôle d'accès) ne sont pas vérifiés.

**Critères d'acceptation :**
- [ ] `GET /api/groups/[id]/tournaments/[tid]/guests` — retourne les accès actifs pour admin, 403 pour non-admin
- [ ] `GET /api/groups/[id]/guests/[accessId]` — retourne l'accès si admin, 403 sinon, 404 si inconnu
- [ ] `GET /api/guest/my-tournaments` — retourne les tournois si accès ACCEPTED, vide si REVOKED, 401 sans auth
- [ ] Les tests sont dans `guest-access.test.ts` ou de nouveaux fichiers dédiés
- [ ] `npm test` passe à 100%

**Effort estimé :** S  
**Dépendances :** TEST-01 (setup seed en commun)  
**Priorité :** 🟠 Important  
**Source :** Rapport

### TS-01 — Typer les pipelines MongoDB avec `PipelineStage[]`

**Contexte :**  
7 usages de `any` dans les repositories de repository MongoDB pour typer des pipelines d'agrégation et des opérations `bulkWrite`. Ces usages sont annotés `// eslint-disable-next-line @typescript-eslint/no-explicit-any` et sont fonctionnellement corrects. Le type `PipelineStage` de Mongoose v7 permettrait d'obtenir une validation TypeScript des étapes de pipeline.

**Fichiers concernés :**
- `src/repositories/db/RoundRepository.ts` (lignes 67, 95, 114, 168)
- `src/repositories/db/TournamentPlayersDeckRepository.ts` (lignes 163, 224)
- `src/repositories/db/TournamentPlayersDeckRepository.ts` (ligne 142 — `bulkWrite` cast)

**Critères d'acceptation :**
- [ ] `import type { PipelineStage } from 'mongoose'` ajouté dans les deux fichiers
- [ ] Les 4 déclarations `any[]` dans `RoundRepository.ts` remplacées par `PipelineStage[]`
- [ ] Les 2 déclarations `any[]` dans `TournamentPlayersDeckRepository.ts` remplacées par `PipelineStage[]`
- [ ] Le `as any` du `bulkWrite` (ligne 142) remplacé par un cast plus précis ou un commentaire justificatif à jour
- [ ] Les `// eslint-disable-next-line` correspondants supprimés
- [ ] `npm test` passe à 100%, `tsc --noEmit` sans erreur

**Effort estimé :** S  
**Dépendances :** aucune  
**Priorité :** 🟡 Mineur  
**Source :** Rapport
