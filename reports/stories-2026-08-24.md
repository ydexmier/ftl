### SEC-01 — Corriger `ApiResponse.serverError()` : message générique côté client

**Identifiant :** SEC-01  
**Priorité :** 🟠 Important  
**Effort :** XS  
**Source :** Rapport (persistant depuis l'audit 2026-08-17)

**Contexte :**  
`ApiResponse.serverError(err)` retourne le message brut de l'exception dans le corps HTTP (ex: `MongoServerError: E11000 duplicate key error collection: ftl.users index: email_1`). Cette information permet à un attaquant de cartographier la structure interne de la base de données. La méthode est utilisée dans 24+ routes.

**Critères d'acceptation :**
- [ ] `src/lib/api/responses.ts` : la réponse HTTP retourne `{ error: 'Une erreur interne est survenue.' }` et non le message de l'exception
- [ ] Le `console.error(err)` existant est conservé pour le log serveur complet
- [ ] Tous les appels existants à `ApiResponse.serverError(err)` fonctionnent sans modification (l'interface publique ne change pas)
- [ ] `npm test` passe à 100%

**Dépendances :** Aucune

### SEC-02 — Corriger l'IP hardcodée dans l'audit log logout

**Identifiant :** SEC-02  
**Priorité :** 🟡 Mineur  
**Effort :** XS  
**Source :** Rapport (persistant depuis l'audit 2026-08-17)

**Contexte :**  
`app/api/auth/logout/route.ts` crée un `AuditLog` avec `ipAddress: 'unknown'` alors que `getIp(request)` est déjà importé dans le même fichier. Toutes les autres routes utilisant `AuditLogRepository.create` transmettent l'IP réelle. - [ ] Aucun autre fichier n'est modifié
- [ ] `npm test` passe à 100%

**Dépendances :** Aucune

### SEC-03 — Planifier la migration du rate limiter vers Redis/Upstash

**Identifiant :** SEC-03  
**Priorité :** 🟡 Mineur  
**Effort :** L  
**Source :** Rapport (persistant depuis l'audit 2026-08-17)

**Contexte :**  
Le rate limiter (`src/lib/auth/rateLimit.ts`) utilise un `Map` Node.js in-process. En déploiement multi-instances (Vercel multi-region, cold starts serverless), chaque instance a son propre compteur indépendant — un attaquant distribuant ses requêtes entre instances contourne la limite. Le compteur est également perdu à chaque redémarrage.

**Critères d'acceptation :**
- [ ] Le rate limiter utilise un store externe partagé entre instances (Redis ou Upstash)
- [ ] L'interface publique `checkRateLimit(key: string)` est préservée — aucun appelant n'est modifié
- [ ] Le comportement est identique en test (mock ou `Map` fallback en `NODE_ENV=test`)
- [ ] `npm test` passe à 100%
- [ ] Documentation de la variable d'environnement requise (ex: `UPSTASH_REDIS_REST_URL`)

**Dépendances :** Décision d'infrastructure (choix Redis provider)

### TEST-01 — Tests d'intégration pour les routes d'approbation invités

**Identifiant :** TEST-01

La route PUT est particulièrement critique : elle couvre 3 branches de transition d'état (approve/reject/revoke), inclut un envoi d'email conditionnel, et vérifie que l'`accessId` appartient bien au groupe demandé.

  - [ ] Retourne 403 si l'`accessId` n'appartient pas au groupe `id`
  - [ ] approve → accès passe à ACCEPTED, email envoyé si l'utilisateur existe
  - [ ] reject → accès passe à REJECTED
  - [ ] revoke → accès passe à REVOKED
  - [ ] revoke sur accès déjà révoqué/expiré → retourne 400
- [ ] `GET /api/groups/[id]/tournaments/[tid]/guests` :
  - [ ] Retourne 401 sans session
  - [ ] Retourne 403 si l'utilisateur n'est pas admin du groupe
  - [ ] Retourne `{ guests: [] }` si aucun accès en attente
  - [ ] Retourne la liste enrichie avec `username` et `email`
- [ ] `npm test` passe à 100%

### TS-01 — Migrer les pipelines MongoDB vers `PipelineStage[]`

**Identifiant :** TS-01

**Effort :** S  
**Source :** Rapport (persistant depuis l'audit 2026-06-08)
